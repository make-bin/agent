1 Agent 建模（Identity / Goal / Capability / Policy / Memory）

design.md §2.2 / §3 —— Agent 不是 Prompt，而是身份、目标、能力、策略、记忆的聚合体

💡⚙️Agent = 五要素聚合体

部分实现

设计思路

Agent 应建模为运行实体：

Agent = Identity + Goal + State + Context + Capability + Policy + Memory + Execution Strategy + Evaluation

五个子模型应内聚在 Agent 聚合根上，Agent Service 负责定义"是谁、能做什么"，不负责 Task 执行。

groundhog 实现

pkg/domain/agent/aggregate/agent_config.go type AgentConfig struct { id, name // Identity systemPrompt // 近似 Goal（无独立 Goal 值对象） description skills []string // Capability mcpServers []string // Capability builtinToolFilter []string }
  • Identity + Capability 落在 AgentConfig 聚合上
  • Policy 不挂在 Agent 上，判定逻辑在 ConfigPolicyChecker（全局配置驱动）
  • Memory 是独立聚合（pkg/domain/memory），靠 userID 关联，非 Agent 组成部分
差异：设计里 Policy/Memory 是 Agent 内聚子模型，实现中被拆到独立 bounded context，是有意识的解耦简化，不算缺陷，但意味着"一个 Agent 的策略"目前是全局/配置级别而非 Agent 实例级别。

2 Task / Session 建模

design.md §2.2 / §28 —— Task 回答"这一次具体要完成什么"

💡⚙️Task 与 Session 双聚合分离

吻合设计

设计思路

Task 定义目标、输入、约束、成功标准、风险、截止时间、执行策略、当前状态。状态机：

CREATED → PLANNING → RUNNING → WAITING/WAITING_HUMAN → COMPLETED/FAILED/CANCELLED/TIMEOUT

groundhog 实现

pkg/domain/runtime/aggregate/task_run.go → TaskRun（单次 Turn 的执行状态） pkg/domain/runtime/vo/task_state.go → TaskState + validTaskTransitions pkg/domain/conversation/aggregate/agent_session.go → AgentSession（跨轮会话） pkg/domain/conversation/vo/session_state.go → Active/Paused/Archived/Compacted

实际是 Task 与 Session 双聚合并存：TaskRun 状态机字段与 design.md 完全一致（IsTerminal() 判终态），AgentSession 管理跨多轮对话的生命周期。

颗粒度差异：TaskRun 的粒度是"一次 Turn"，而非设计文档设想的可能跨越更长生命周期、多步骤的任务；长任务目前靠 Session 内多个 TaskRun 串联体现，而非单个 Task 内部的多阶段状态迁移。

3 执行范式（Execution Strategy）

design.md §4-9, §47 —— Direct / ReAct / Workflow / Plan&Execute / Multi-Agent / HITL 插件化

💡⚙️ExecutionStrategy 插件接口

骨架完整，2/6 范式可用

设计思路

Runtime 不应为每种范式单独建服务，而是统一接口，插件式存在：

initialize / decide / execute / observe / next / shouldReplan / shouldSwitchStrategy

  • DirectStrategy / ReactiveStrategy / WorkflowStrategy
  • PlanningStrategy / MultiAgentStrategy / HITLStrategy

groundhog 实现

pkg/domain/runtime/service/execution_strategy.go interface ExecutionStrategy { Kind() Decide() Execute() Observe() Next() ShouldReplan() ShouldSwitchStrategy() } pkg/infrastructure/adk/strategy_factory_impl.go ✅ ReactStrategyImpl （strategy_react.go） ✅ PlanningStrategy （strategy_planning.go） ⚠️ WorkflowRunner （strategy_workflow.go，Decide 未实现，仅占位） ❌ StrategyMultiAgent （无对应类型，Create 直接报错）

DefaultStrategySelector.Select：高复杂度+低确定性 → Planning，其余 → Reactive；MultiAgent=true 或 Determinism=High 时代码注释明确写"降级回 Reactive"。Direct 范式靠 ReAct 首轮无 tool_calls 自然退化实现，不单独探测。

差异（较大）：六种范式中只有 ReAct、Planning 真正可跑；Workflow/MultiAgent 是接口占位，Adaptive 切换接口（ShouldSwitchStrategy）已定义但主循环并未真正驱动策略切换生效于生产路径。

4 Agent Runtime 核心循环

design.md §13 —— Task → Strategy → Decision → Action → Executor → Observation → State Update → Continue/Replan/Switch

💡⚙️runViaExecutionStrategy() 主循环

吻合设计

设计思路

统一执行闭环，是整个平台 Runtime 的核心：

Task → Strategy → Decision → Action → Executor → Observation → State Update → Continue/Replan/Switch → Complete

groundhog 实现

pkg/infrastructure/adk/runner_adapter.go RunnerAdapter.Run/RunWithOptions → runViaExecutionStrategy() (约514-870行) for i := 0; i < maxIter { decision := strategy.Decide(ctx, taskRun) // Decision if decision.Action == nil { return decision.Text } obs := strategy.Execute(ctx, decision.Action) // Action → Executor taskRun.AppendAction(...) // State Update strategy.Observe(ctx, obs) // Observe r.saveCheckpoint(ctx, taskRun, action.ID) // Checkpoint if strategy.Next(ctx) { break } if strategy.ShouldReplan(ctx) { ... } // Replan if strategy.ShouldSwitchStrategy(ctx) { ... } // Switch }

每完成一个 Action 都会调用 saveCheckpoint，精确对应 design.md §38 的 "Action Completed → State Update → Checkpoint → Next Step"。循环有 MaxToolIterations 兜底。

5 Planner

design.md §19 —— Planner 决定做什么，Executor 真正去做

💡⚙️LLMPlanner（仅 Planning 分支生效）

部分实现

设计思路

Understand → Decompose → Dependency → Schedule → Plan，Planner 可调用 LLM，但不拥有 Tool 执行权、State 持久化责任、Retry/Permission/Checkpoint 控制权。

groundhog 实现

pkg/domain/runtime/service/planner.go → Planner 接口 pkg/infrastructure/adk/... → LLMPlanner(NewLLMPlanner(llmWithTools)) pkg/domain/runtime/entity/plan.go → Plan{ Steps []Step } Step{ DependsOn, State vo.StepState } Plan.NextReadySteps() // 依赖解析

PlanningStrategy.Decide（strategy_planning.go）首次调用 Planner 生成 Plan。代码注释直接引用了 design.md §19 原话"Planner = 决定做什么, Executor = 真正去做"。

差异：Planner 仅在 Planning 策略分支生效；ReAct 分支完全隐含在 LLM tool-calling 循环里，没有显式 Plan/Step 概念，这是范式本身的合理差异，不是缺陷。

6 Executor / Tool Gateway

design.md §18, §31 —— 把 Runtime 决定的 Action 安全、可靠地执行出来

💡⚙️ExecutorImpl + ToolAdapter

吻合设计

设计思路

Action → Policy Check → Authorization → Capability Resolve → Execute → Observation。Executor 不做业务决策，不控制 Checkpoint 或 UI。

groundhog 实现

pkg/infrastructure/adk/executor_impl.go → ExecutorImpl.Execute() 1. PolicyChecker.Check(ctx, action) // Policy Check 2. if RequireApproval: Approver.RequestApproval // Authorization 3. builtin_tool_filter 白名单校验 4. ToolAdapter 分发 → MCP / Builtin tools // Capability Resolve + Execute pkg/infrastructure/adk/tool_adapter.go → MCPManager / BuiltinSchemas() / Tools()

默认注入 AllowAllPolicyChecker / NoopApprovalGate，CLI 启动时（gateway.go）显式替换为生产实现 ConfigPolicyChecker / ManagerApprovalGate，符合"平台默认安全、可插拔覆盖"的设计取向。

7 State 模型

design.md §15 —— Task State / Plan State / Action State / Approval State / Error State / Artifact State

💡⚙️多层状态机 + PostgreSQL 持久化

部分实现

设计思路

State 必须作为一等公民，至少包含 Task/Plan/Action/Approval/Error/Artifact 六类状态，用于恢复、查询、当前执行判断。

groundhog 实现

pkg/domain/runtime/vo/task_state.go → TaskState（完整转移表） pkg/domain/runtime/vo (ActionState) → Action.State pkg/domain/runtime/vo (StepState) → Plan Step 状态（仅Planning分支） pkg/domain/conversation/vo/session_state.go → SessionState pkg/infrastructure/persistence/session_repository_impl.go → PostgreSQL 持久化

Task/Action/Step/Session 四类状态机均已定义，命名与转移表和 design.md 高度一致。

差异：TaskRun 状态目前只存在内存里，TaskRunRepository 只有接口没有实现，进程重启或多副本部署下无法恢复/跨 Turn 追踪；只有 Session 级状态和 Checkpoint 落了 PostgreSQL。

8 Event 与 State 分离

design.md §16, §35 —— State = 当前事实，Event = 过去发生了什么，两者不能混为一谈

💡⚙️EventBus（进程内） + SSE（独立通道）

部分实现

设计思路

Event Bus 应解耦 Runtime 与下游（A2UI / Trace / Audit / Evaluation），事件涵盖 task/plan/step/action/tool/state/approval/artifact 全生命周期。

groundhog 实现

pkg/application/eventbus/eventbus.go EventBus{ Publish() 同步调用所有handler, 按 reflect.TypeOf 路由 } 事件示例: runtimeEvent.NewStrategyChanged, event.NewAgentTurnStarted, event.NewSessionCompacted (EventType()=="agent.session.compacted") pkg/application/service/agent_app_service.go → StreamTurn() 独立编码 dto.StreamEvent{Type: chunk/thinking/tool_start/tool_done/ approval_required/done/error} → SSE

SSE 推送不经过 EventBus，是 agent_app_service.go 直接把回调编码成 StreamEvent 写入 channel 再转 SSE。pkg/interface/ws 下是 WebSocket JSON-RPC（cron），非 SSE 主链路。

差异：EventBus 是进程内同步内存实现（sync.RWMutex + map），不落库、不进 MQ，重启丢失，无法真正喂给独立的 Audit/Evaluation 下游；且 EventBus 与面向前端的 SSE 是两条独立机制，未合一，与设计文档"Event Bus 解耦 Runtime 与所有下游"的构想有差距。

9 Policy

design.md §22 —— Policy 不能依赖 Prompt 实现，必须由平台判定 ALLOW/DENY/REQUIRE_APPROVAL

💡⚙️ConfigPolicyChecker + actionwhitelist

吻合设计

设计思路

正确方式：Runtime → Policy Service → ALLOW / DENY / REQUIRE_APPROVAL，典型规则如"高风险操作需要审批""角色不匹配则拒绝""超额需要审批"。

groundhog 实现

pkg/infrastructure/adk/policy_checker_impl.go ConfigPolicyChecker.Check(ctx, action) (vo.PolicyDecision, string, error) vo.PolicyDecision: PolicyAllow | PolicyDeny | PolicyRequireApproval 判定规则(requiresApproval)： ① 内建危险工具硬编码名单 → 始终需审批 ② MCP server 级 require_approval 配置 ③ MCP server 级 dangerous_tools 精确匹配 ④ vo.SourceUIAction 独立的 ui_action_dangerous_tools 名单 pkg/application/actionwhitelist/whitelist.go Whitelist：按最近一次 Turn 的 ProposedAction 校验 UI 提交的 Action ID（纯内存）

代码注释直接引用 design.md §22 原话："policy must be enforced by the platform, not by prompt instructions"。Policy 与 Prompt 解耦这条核心原则严格落地。

小差异：actionwhitelist 纯内存无持久化，进程重启即清空（代码注释承认这是可接受的权衡）；ToolPolicyService（领域层）有定义但零调用，细粒度领域化 Policy 尚未接入，目前完全靠配置驱动的 ConfigPolicyChecker。

💡⚙️Memory 聚合（仅 Semantic 真正落地）

部分实现

设计思路

Memory 与 Conversation History 不应混为一谈，应分 Working（临时）/ Episodic（经历）/ Semantic（长期事实）/ Procedural（流程经验）四类。

groundhog 实现

pkg/domain/memory/aggregate/memory.go → Memory{ kind vo.MemoryKind } pkg/domain/memory/vo/memory_kind.go → MemoryWorking/Episodic/Semantic/Procedural pkg/domain/memory/service/embedding_provider.go → EmbeddingProvider 接口 pkg/infrastructure/adk/openai_compat_embedding.go → OpenAI兼容embedding实现

11 Human-in-the-loop

design.md §10 —— HITL 是 Runtime 一级能力，不是异常流程

💡⚙️Approval Manager（阻塞式 channel）

部分实现

设计思路

WAITING_HUMAN → APPROVED → RESUME 或 WAITING_HUMAN → REJECTED → TERMINATED，应显式建模为一级状态。

groundhog 实现

pkg/domain/runtime/vo/task_state.go TaskWaitingHuman = "WAITING_HUMAN" // 合法转移目标之一 pkg/infrastructure/adk/approval_gate_impl.go ApprovalGate → approval.Manager.RequestWithID（channel阻塞等待） Decision: DecisionApprove | DecisionDeny（仅两态） agent_app_service.go: ApprovalRequiredCallback → dto.StreamEvent{Type:"approval_required", Approval:{ApprovalID,...}}

SSE 侧发出 approval_required 事件，前端调用 HTTP 接口触发 approvalMgr.Resolve 完成审批。

差异：TaskState 里确有 WAITING_HUMAN 状态定义，但审批发生时 TaskRun 状态字段没有跟着切到 TaskWaitingHuman，真正的等待/决策逻辑落在 approval.Manager 的 channel 模型上，两套机制状态机定义完整但未完全同步串联。

12 Durable Execution / Checkpoint / Recovery

design.md §38 —— 长任务必须支持 Pause/Resume/Retry/Recovery/Checkpoint

💡⚙️Checkpoint 写路径完整，Recovery 消费路径缺失

部分实现，是最大缺口之一

设计思路

Step Started → Action → Completed → State Update → Checkpoint → Next Step；故障后：Load Latest Checkpoint → Restore State → Idempotency Check → Resume。

groundhog 实现

pkg/domain/runtime/repository/checkpoint_repository.go Checkpoint{ TaskRunID, ActionID, MessagesSnapshot, CompletedAt } CheckpointRepository{ Save, FindLatest } runner_adapter.go: saveCheckpoint() 每个 Action 完成后写入一次（best-effort，失败仅记日志） gateway.go: 注册 persistence.NewCheckpointRepository()

CompactionService（上下文窗口压缩）不是恢复机制，与 Checkpoint/Recovery 是完全不同的关注点，不应混为一谈——这点在原始设计讨论中容易被误解，特此澄清。

差异（较大）：Checkpoint 只落地了"写"路径，没有找到进程重启后自动 FindLatest 并续跑 in-flight TaskRun 的代码；TaskResumed 事件只是占位，代码注释明确写"自动扫描恢复排除在范围外"。Recovery 是设计与实现之间差距最大的环节。

13 Multi-Agent

design.md §9 —— 在能力/Context/Permission/生命周期边界明确时使用多 Agent

💡⚙️AgentDelegationFlowRunner（P2P ping-pong，非 Supervisor）

部分实现，路径不同

设计思路

典型结构是 Supervisor 统一调度多个专业 Sub-Agent：

Supervisor → OrderAgent / ShippingAgent / PolicyAgent

groundhog 实现

pkg/application/service/agent_delegation_flow.go AgentDelegationFlowRunner： Step1 投递消息给目标agent Step2 ping-pong循环（MaxPingPongTurns限制，ReplySkipToken提前终止） Step3 向发起方channel播报摘要 pkg/infrastructure/adk/tool_agent_delegation.go → SessionsSendTool ("sessions_send") pkg/infrastructure/adk/agents_list_tool.go → AgentsListTool (仅列出 Discoverable=true 的Agent)

14 A2UI 集成

design.md §23-24 —— Agent Runtime → A2UI Planner → A2UI Spec → A2UI Gateway → Render SDK

💡⚙️a2ui-gateway 单向适配 groundhog 既有 REST/SSE API

吻合设计（含安全缺口）

设计思路

Agent Runtime 不应直接操作 UI：产生 Event/Artifact → A2UI Planner 转换为 UI 描述 → A2UI Gateway 负责 Session/鉴权/协议/连接/Action转发 → Render SDK 渲染。

groundhog / a2ui-gateway 实现

a2ui-gateway/internal/orchestrate/groundhog_client.go GroundhogClient.EnsureSession → POST /api/v1/sessions GroundhogClient.StreamTurn → POST /sessions/:id/messages/stream (SSE) GroundhogClient.SubmitAction → POST /api/v1/sessions/:id/actions a2ui-gateway/internal/orchestrate/orchestrator.go Orchestrator.runTurn/HandleAction → planAndDispatch() → a2ui-planner.Plan() → router.Router.Dispatch() 扇出给前端连接

groundhog 侧对 A2UI 完全无感——代码注释写"the subset of groundhog's existing, unmodified REST API"，是 a2ui-gateway 单向适配。SubmitAction 取代了早期"把 Action 编码成自然语言塞进 user_input"的方案，可靠性更高。

安全缺口：a2ui-gateway 完全没有鉴权（代码注释直写 "Authentication has been intentionally removed"），GET /ws 只检查 session_id 非空，任何人拿到 session_id 即可冒充收发；originAllowlist=["*"] 形同摆设。生产暴露前必须补齐认证层。
流程差异：Action 提交直接打 groundhog，并不经过 A2UI Planner 回路中心，与 design.md §24 流程图字面描述不完全一致（属于合理简化：等 groundhog 产生新结果后由上游再调一次 /plan）。

15 Model Gateway

💡⚙️ModelAdapter + FallbackLLM

吻合设计

设计思路

Model Gateway 负责 Model Routing、Fallback、Rate Limit、Token Accounting、Multi-Provider；Agent Runtime 只关心 Generate / Structured Output / Tool Calling / Reasoning。

groundhog 实现

pkg/infrastructure/adk/model_adapter.go ModelAdapter{ providers map[vo.ProviderType]ModelFactory } ToADKModel() → 按 ProviderType 路由 pkg/infrastructure/adk/openai_compat.go OpenAICompatProviderFactory（BaseURL/APIKey 优先级链） pkg/infrastructure/adk/fallback.go FallbackLLM.GenerateContent/Stream：主模型失败 → 按FallbackChain()顺序重试 → 发送 ModelFallbackTriggeredEvent{FailedModel, FallbackModel, Reason}

17 Sandbox 执行（groundhog 特有扩展）

design.md 未定义此层 —— 属于 groundhog 对 Executor / Tool Gateway 能力的纯增量扩展

⚙️K8sExecutor + PoolManager

groundhog 增量能力

设计思路（design.md 未覆盖）

设计文档定义了 Tool Gateway 需要支持 REST/gRPC/MCP/Database/External API 等接入方式和治理能力（认证、限流、重试、熔断），但没有专门定义"隔离沙箱执行"这一能力形态。

groundhog 实现

pkg/infrastructure/sandbox/k8s_executor.go K8sExecutor：通过 K8s exec API 在沙箱 Pod 内执行命令（clientset/restConfig） pkg/infrastructure/sandbox/pool_manager.go / pool_manager_impl.go PoolManager：基于 skill_config 变化对 SandboxTemplate CRD + K8s Secret 做 server-side apply（fieldManager:"groundhog"，支持多副本部署不冲突）

让 Runtime 的 Tool Gateway 除了本地 builtin tool/MCP 之外，还能把 run_process 等工具路由到隔离的 K8s Pod 沙箱里执行，池化管理避免每次调用现建 Pod 的冷启动开销。

定位：这是 groundhog 面向生产环境（代码执行类技能需要强隔离）做的增量扩展，不是对设计文档的偏离，而是设计文档抽象层级之下的具体落地选择之一。

◆ 差异总览与优先级建议

综合 17 个功能点核实结果，按严重程度归类（详细清单见 docs/plan/design-vs-implementation-gap-analysis.md）

🔴 高优先级 / 安全风险

  • a2ui-gateway 完全无鉴权，任何人拿到 session_id 即可冒充会话收发消息，生产暴露前必须补齐
  • 多执行范式未全部生效：Workflow / MultiAgent 策略是空壳，Adaptive 切换主循环未真正调用
  • Durable Recovery 未自动化：Checkpoint 只写不读，进程重启后 in-flight TaskRun 无法自动续跑

🟡 中优先级 / 影响可靠性

  • TaskRun 状态无持久化（只有接口没有实现），多副本/重启场景状态丢失
  • Event Bus 是进程内同步内存实现，不落库不进 MQ，与 SSE 是两条独立机制未合一
  • HITL 的 TaskState.WAITING_HUMAN 与 ApprovalManager 的 channel 阻塞模型未完全同步
  • Memory 四类中仅 Semantic 真正落地，Working/Episodic/Procedural 名存实无

🟢 低优先级 / 设计取舍

  • Observability / Evaluation 仅 doc.go 占位，尚未开始实现（工作量较大，需专项排期）
  • Multi-Agent 是 P2P ping-pong 而非 Supervisor 层级调度（架构选择，非缺陷）
  • a2ui-planner 是纯规则引擎不含 LLM（预留了替换接口）
  • Action 回流未经过 Planner 回路中心，是简化后的"间接回流"
功能点状态核心结论
1. Agent 建模部分Identity+Capability 落地，Policy/Memory 解耦到独立 context
2. Task/Session吻合TaskRun + AgentSession 双聚合，状态机与设计一致
3. 执行范式部分仅 ReAct/Planning 可用，Workflow/MultiAgent 占位
4. Runtime 循环吻合Decide→Execute→Observe→Checkpoint 闭环完整
5. Planner部分仅 Planning 分支有显式 Plan/Step
6. Executor吻合Policy→Approval→Tool 链路完整可插拔
7. State 模型部分状态机定义完整，TaskRun 未持久化
8. Event/State 分离部分EventBus 为内存实现，与 SSE 未合一
9. Policy吻合与 Prompt 解耦彻底，ALLOW/DENY/REQUIRE_APPROVAL 落地
10. Memory部分四类仅 Semantic 真正使用
11. HITL部分Approval 机制可用，与 TaskState 未完全同步
12. Durable/Recovery部分Checkpoint 写路径完整，Recovery 消费缺失
13. Multi-Agent部分P2P ping-pong，非 Supervisor 层级
14. A2UI 集成吻合(有缺口)链路吻合，但 Gateway 无鉴权
15. Model Gateway吻合多 Provider + Fallback 链已实现
16. Observability/Evaluation未实现仅 doc.go 占位
17. Sandbox增量能力design.md 未定义，groundhog 生产扩展
